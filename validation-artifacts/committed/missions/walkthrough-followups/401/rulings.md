3. **Filenames, R145 self-ruled (the issue's proposed solution, plus call 6).** The pattern is `<road>_<kind>_<YYYY-MM-DD>_<fingerprint>`, for example `East-Colfax-Avenue_shoulder_2026-10-27_3fa91c`. The road is the confirmed road's OSM name, or its ref when it has no name. The kind is the scenario kind with "_" turned into "-" (`flagger-lane-closure`). The day is the downloading browser's local date. The format is CHOSEN (non-safety): an ISO date because it sorts. The road is spelled the way OSM spells it, with no abbreviation map, so the name never says something OSM doesn't (Rule 10). My first version had no fingerprint. Its residual (two sides of one road, or two lengths, on one day share a name) broke acceptance line 2, and the review caught it. Call 6 fixes it.
4. **Saved plans are untouched.** `/api/plans/<id>/<kind>` names files from `row.name` on the server (`lib/render-proxy.ts:608`), and the client keeps that name (`downloadSavedPart`). 6. **Repair cycle 1 (review item 1): a plan fingerprint in the name, R145 self-ruled, CHOSEN.** `planFingerprint()` (`lib/download-name.ts`) is FNV-1a 32-bit over `JSON.stringify` of the scenario as sent (`downloadScenario`, the object the cards, the quote panel, the zip button and the bundle body all carry), with `site_scan.token` removed. The first 6 hex characters go last in the base name. A new token for the same inputs is the same plan, so the name holds when the same plan is downloaded again, and any change to the plan (side, length, anything sent) gives a new name. Six hex characters is CHOSEN, non-safety: about 16.7 million values, so two plans in one session practically never share one, and it's short enough to read. It isn't a security hash. The zip button now names from `downloadScenario` (it used `scenario`), so its fingerprint matches the cards'. Project-named plans get no fingerprint (unchanged).
