## What exists today (base `cf5ddffd`)

- `src/rendering/static_aerial.py` `question_image_url`: the line loop drops the farthest lines once the URL would pass `URL_MAX_CHARS - 200`, and returns only `bool(dashes)`. `src/api/render_api.py` then hands `cross.lines` (every line, drawn or not) to `cross_tag_box`.
- `src/rules/site_detection.py` `cross_street_from_elements`: the worked road is dropped by `name.lower() == road_name.strip().lower()` or by the 25° bearing test (`CROSS_STREET_PARALLEL_DEG`, CHOSEN, R145-3 of #484).
- The repo has no street-name normaliser. Searched `src/`, `conestruct/site/lib/`, `tests/` for `normali[sz]e`, `canonical`, `ave`, `blvd`, `Avenue`: the only normalisers are `normalize_glyphs` (PDF glyphs), `normaliseCoordText`, `normaliseBearing`, `normalizeChainLink`. None reads a street name.

## R145 self-ruled

**R145-1. The tag walks only the lines drawn.** `question_image_url`'s fourth value becomes the list of lines it drew (each drawn whole, nearest first), in place of the bool. Its truthiness is the bool's (a line is listed only when it put a dash in the URL), so `x-map-subject` and every URL are unchanged. The route passes that list to `cross_tag_box`, so the tag can only sit beside dashes the image has (Rule 10). `cross_tag_box` itself is unchanged.

**R145-2. The name match goes through a small street-name key, not way ids.** No normaliser exists, so one is added beside its one reader (`_street_key` in `site_detection.py`): lower-case, punctuation to spaces, and each word mapped through a table of the common directional and street-type abbreviations to one form. The table is CHOSEN (Rule 12; not a safety number: it only decides which way the map draws). It errs toward no match: a word it doesn't know is compared as written, so an unmatched mainline still meets the 25° test exactly as today.
Repair cycle 1 (independent reviewer, Rule 10): the key keeps every Unicode letter and digit (`casefold`, `[\W_]+` to spaces). The first cut's `[^0-9a-z]+` reduced every Cyrillic name to `""` and "Calle José"/"Calle Josè" to "calle jos", so unrelated ways grouped as one street under one tag. A name that is all punctuation keys as itself; only an empty name keys as `""`, and an empty key never matches.
Known limit, not fixed: a single-letter street collides with a spelled-out direction ("N St" and "North St" both key "north street"; "Avenue N" and "Avenue North"). If the worked road and a crossing way collide this way, the real cross street is dropped and no line is drawn (absence, not a wrong line). The old exact-name drop could already fail like this when the names matched as written.
Why not the OSM way id: the route has no way id for the worked road (`meta` carries `roadName`, not a way), so it would take a second Overpass read at the pin, and OSM splits ways at intersections, so the way at the pin is often not the way through the crossing. The name key needs no new read.

**R145-3. Same-named parts group by the same key.** The cross street's other parts are gathered by `_street_key` too, so "Park Ave" and "Park Avenue" parts of one street draw together. The tag keeps the nearest part's name as OSM writes it. Folded in under R154: same function, a few lines, no ruling or source needed.
Known limits (repair cycle 2, not fixed): the single-letter collision in R145-2 ("N St" and "North St") can also group two different crossing ways under one tag (`cross_street_from_elements`, the grouping line); very unlikely, since both would have to pass within 30 m of one crossing. The lone `s` to "south" mapping also rewrites "U.S. 6" as "u south 6"; harmless, since both sides of a comparison are rewritten the same way.

**R145-4. #484's E Colfax output stays byte-identical.** The fixture's mainline parts are all "East Colfax Avenue" and its other streets are "Franklin Street" and "Park Avenue"; each key matches only its own name, so the pick, the lines and the URL are the same. Proved by `scratchpad` comparison, recorded in `evidence.md`.

**R145-5. Unicode normal form (repair cycle 2).** `_street_key` applies NFKC before `casefold`: a decomposed accent (NFD combining mark) is otherwise a `\W` character and was stripped, so "Calle José" (decomposed) keyed like "Calle Jose" and "Calle Josè", while the precomposed "José" keyed differently from its own decomposed form. A decomposed accent keys like its precomposed letter **only when a precomposed character exists**; any other mark is still stripped (R145-7). The `_street_key` docstring over-claims this ("Every Unicode letter and digit is kept"); it is left as is because both repair cycles were used, and #502 notes the fix. NFKC also maps full-width digits ("１st Ave") to ASCII. Probe output: `probe.txt`.

**R145-6. The picker's own mainline drop is filed, not folded.** `conestruct/site/lib/road-detection/cross-street.ts:112` still drops the mainline by raw `toLowerCase`, so map and picker now disagree on abbreviated names. A different file, another surface and a vitest suite: outside the R154 fold test. Filed as #501 (priority-low, frontend).

**R145-7. Combining marks with no precomposed form: a known limit (orchestrator call, round 3).** `[\W_]+` still strips a combining mark that NFKC cannot fold into a precomposed letter: Devanagari and Thai vowel signs, q + combining acute, and the dot `casefold` leaves from "İ". So "किला मार्ग" and "कुली मार्ग" share a key (checked on this branch), which can group different ways under one tag or drop the real cross street. Accepted for now: the product's jurisdictions are in Colorado, whose OSM names are US English, so the risk is very low. Both repair cycles were used, so no code changed. Filed as #502 (bug, priority-low, backend). Flagged to Ryan in the mission report.

**R145-8. The `TAG_CHAR_PX` comment (Ryan's owner comment on #487, round 4).** Ryan put in scope the comment above `TAG_CHAR_PX` in `src/rendering/static_aerial.py`, which claimed "the box checked is never narrower than the tag drawn". That overclaims. Measured (round 5, `tag-widths.txt`: `@fontsource/inter@5.0.16` `inter-latin-600-normal.woff`, sha256 `93b3d09b…`, 2816 upm, fontTools advance widths at 12.5 px): 8 px is wider than every lowercase letter except m (11.2) and w (10.5); most capitals (W 12.6, M 11.3, A–Z mostly 8.0–9.7) and the digits 0 3 4 6 8 9 (8.1–8.3) set wider. "Franklin Street" measures 110.8 px with chrome against a 142 px box; "MOUNT MORRISON RD" 160.9 px against 158 px. So a mixed-case name usually fits, but a capital-heavy name can draw wider than the box checked. The comment now says this; no code line changed. (Round 4's wording, "every letter except W and M", was itself wrong and is replaced.) Checking the measured width is left out: it is a behaviour change, both repair cycles were used, and it needs a sourced width table for Inter 600 (or a frontend measure). Filed as #503 (priority-low, backend).
