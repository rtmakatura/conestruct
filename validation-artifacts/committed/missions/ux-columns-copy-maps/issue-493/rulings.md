# #493 rulings

Ryan's brief, verbatim: "#484: the intersection map reuses the cross street the WHERE tap already found (#440) instead of a new lookup; record the time saved."

**R145-1 (R145 self-ruled). The tap keeps the geometry it already fetched.** The tap's record (`meta.intersection`, `intersectionRecord` in `conestruct/site/lib/road-detection/cross-street-lookup.ts`) carries the point, name, class and speed, not the line #484 draws. The `/api/road-bearing` answer the tap reads already has the cross street's line (`RoadCandidate.geometry`, `lib/road-detection/types.ts`: "this candidate's OSM way geometry, extended server-side by walking connected same-name/ref ways ... capped at 300 nodes"). The smallest honest change is to keep it: `deriveCrossStreet` copies it onto the candidate, `intersectionRecord` writes it as `meta.intersection.geometry`. No new read, no new producer: the picker's Save and the band's tap share `intersectionRecord` (#440 ruling 3, one producer). It is a relayed fact like `meta.centerline` (#140); the backend picks and draws (Rule 3).

**R145-2 (R145 self-ruled). The record is used only at the question's crossing.** The intersection question frames on the scan's nearest crossing node; the tap marks the crossing the operator chose. The backend reuses the record only when the tapped point lies within `CROSS_STREET_RADIUS_M` (30 m, #484 R145-2's CHOSEN radius, reused, not a new number) of that node and the record's line passes within the same radius of it. Otherwise the record is about another crossing, and #484's lookup runs (no silent substitution, Rule 10).

**R145-3 (R145 self-ruled). Which path ran is said.** `x-map-cross-source: tap | lookup` on every intersection full image that sought a cross street (none on the soft image or other questions, which seek none), and a log line. The proxy relays it beside `x-map-frame`, for the checks; the card reads nothing new.

**R145-4 (R145 self-ruled; amended in repair cycle 1). The optional line never refuses a plan.** Cycle 0 capped `IntersectionPin.geometry` at 300 points with `max_length`, which the independent reviewer showed would 422 every route for a whole plan (saved plans included) when the lookup kept an own-way line over 300 points: `/api/road-bearing` sets the own-way geometry as the baseline and only the stitch path trims to `GEOMETRY_MAX_NODES` (`lib/road-detection/stitch.ts:46`), and the stitch can be skipped or fail. Now: the frontend's `intersectionRecord` writes the line only with 2 to 300 points (a longer one is left out, not cut on the frontend: cutting is geometry, Rule 3); the backend's before-validator drops (None, a log line) any line that isn't 2 to 300 finite, in-range `[lat, lng]` pairs, and the map runs #484's lookup (`x-map-cross-source: lookup`). 300 is CHOSEN (not a safety number): the producer's own cap. Measured against the 32 KB cap: the largest capped browser body (bundle / quote-breakdown, a maximal scenario) is 21,370 bytes and the largest upstream body (proxy -> Modal, with the derived centerline) 29,221 (`size-measurement-bodies.txt`); the 24,312-byte figure the vitest holds is the default scenario's upstream needs-you body, not the worst case.

**R145-5 (R145 self-ruled). "Match #484's output" is read as the same picture, not the same URL.** #484 draws each OSM way it found near the crossing (Franklin Street, 3 ways); the tap's line is the same street stitched into one chain. Dash phase restarts at each way in #484, so the URL bytes differ. The test holds what the operator sees: the same frame and point, the same name, the tag at the same place, and every #484 dash lying on the tap's line.

**R145-6 (R145 self-ruled; reworded in repair cycle 1). Timing: one live read, stated as one sample.** The #484/#486 evidence has only the whole first-image times on prod (1061 / 1468 / 504 ms in the § 4 table, `ux-token-map-load-edit/prod-check/outcome.md:70-72`, the rerun; 3865 ms at 1198 on the first run, `outcome.md:15`, which collided with the permanent check and was rerun, § 6, `outcome.md:97-98`), not the cross-street read alone. The saving is stated as one Overpass read per crossing's first image, bounded by the 8 s budget, not as a prod figure. Nothing in the tests calls Overpass.

**R145-7 (R145 self-ruled, repair cycle 1). The offset crossing folds in.** The reviewer's optional case (two cross streets within 30 m; the tapped one is drawn) is one test in a file this branch already touches, needs no ruling, fits the amended prediction and is under 20 lines of code under test (none): folded in (R154 fold test). Everything else in #487 stays with #487.

**R145-8 (R145 self-ruled, repair cycle 2; was "Noted, not fixed" in round 2). A coordinate past float range drops the line.** `_usable_line` (`src/api/schemas.py`) called `math.isfinite` before its range check, so a JSON integer of more than 308 digits raised `OverflowError` (int too large to convert to float): a 500 on every route that reads `meta`, for a hand-made request only. Now the range check runs first (Python compares a huge integer with a float exactly), `float()` is guarded against `OverflowError` / `TypeError` / `ValueError`, and any of them drops the line like every other unusable one. Tested: `[[10**400, 0], [0, 0]]` is dropped, the map runs the lookup, and `/render/audit`, `/render/markdown` and `/render/xlsx` answer 200 with the audit equal to the plan with no line. Folded in under R154 (same file, no ruling, about 10 lines).

**R145-9 (R145 self-ruled, mission retap-and-cap). The #112 guard leaves the line out.** Gate finding: `applyCrossStreetCandidate` compared `JSON.stringify(crossStreet)`, which this branch made include `geometry`; the line differs between taps of the same street (trimmed around the snapped point, or the whole own way when the stitch fails), so a re-tap replaced the operator's edited approaches, cleared `detectionOverrides` and put the lane hold back on. Now the guard and its memory use the candidate without `geometry`. The approaches never read the line (`approachesFromCrossStreet`), and `meta.intersection.geometry` is written by `intersectionRecord`, not the apply, so a re-tap still refreshes the line the map draws. Tested where the bug lives (`cross-street-apply.test.ts`): a re-tap with a different line, or with no line, keeps the edited approach, the overrides and the hold off; a different street with the same line still replaces. Red on the unfixed guard: `red-proof-retap.txt` (2 of 3 new tests failed; the different-street case passes on both, as it should). Existing source, no new number, no ruling needed.

**R145-10 (R145 self-ruled, retap-and-cap gate round 1). The tap path tells the worked road by `_street_key`.** Reviewer finding: `tapped_cross_street` compared names with plain `.lower()`, while #487 (in the base, `cross_street_from_elements`) compares `_street_key`, so at a bend past 25° a tapped line named "E Colfax Ave" on the road "East Colfax Avenue" was drawn as the cross street. Now both paths use `_street_key`, an empty key never matching (as #487). Source: #487's own rule in the base; no new number, no ruling needed. Tested and red-proved (`red-proof-tap-street-key.txt`).
