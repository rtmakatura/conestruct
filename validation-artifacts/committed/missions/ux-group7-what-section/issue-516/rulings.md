## R145 self-ruled (CC, 2026-11-11)

- **R145-1, where the fix goes: the caller that builds the request.** The stale request is the load ahead (`WhereBand.tsx` `ahead`, sent by `BandAerial.tsx:323` through `prefetchGeometry`), confirmed by a stack in the mounted test (red-proof.txt). The save paths are already clean. So the fix is in the load ahead, not the Save: a load-ahead answer is built only from the geometry answer to the scenario on screen. The issue's second option (strip `work.travel` when `confirmedRoad` is null) is not taken: it would mirror a backend rule in the frontend (Rule 3) and still build ahead reads from another pin's answer.
- **R145-2, how the load ahead knows the answer is current: the hook stamps it.** `useCorridorGeometry` sets `for` (the scenario's JSON, the key it already computes) on each ready answer it serves; the load ahead compares it with `JSON.stringify(scenario)`. `state === "ready"` alone is not enough: for the render after the Save the hook's state is still the old pin's `ready` answer (its effect has not run), and `loading` keeps the previous geometry. Stamping is additive (an optional field) and no other consumer reads it, so the side question, the aerial, the picker preview and #440 X20's side clear render as before. Changing the hook to report `loading` on that render was not taken: it reaches every consumer and would add a loading render to a remembered answer (#456 M12).
- **R145-3, the test.** One mounted-flow test through `GeneratorShell` (the picker stubbed, as in `WhereBand.edit-on-map-line.test.tsx`, to return what the real picker saves after a failed lookup and a direction tile: `confirmedRoad: null`, `roadAxis: "north_south"`; `/api/road-bearing` answers 504 after the move). The geometry mock answers the backend's 400 `pin_model_input` for a road-less `work.travel`. It asserts that every geometry read with `roadAxis` and no road carries no `work.travel`, that the load ahead still runs from the direction's sides (`work.heading`), and that #488's line is shown once with the side unanswered.
- **R145-4, why prod saw one 400 and the test two** (found by the item's independent reviewer, cites checked by subject). At the reproduction's first pin (39.73997, -104.96632), East Colfax is a grouped divided street: the main way is `oneway: "yes"` and has a twin (`validation-artifacts/committed/missions/ux-group8-map-window/prod-check/logs/run1-1440.log:14`: `"road":{"way":"600545936",...,"oneway":"yes"},"twin":{"way":"1548771425","bearing":270.12}`, side options "South side · eastbound traffic" and "North side · westbound traffic [twin]"). The backend builds the twin's option with `"work": {"side": "right", "travel": travel}` for each travel the twin's one-way direction allows (`src/api/render_api.py:1761-1773`), so the twin's option is also `{side: right, travel: with_geometry}`, the same `work` as the main way's. The two load-ahead scenarios are therefore the same JSON, and `readGeometry`'s in-flight map (`conestruct/site/lib/corridor-geometry.ts:300-301`, `geoInflight.get(key)` returns the read already on its way) sends one request: the one 400 prod showed. The test's old road is two-way, so its two sides have different `work` (`with_geometry`, `against_geometry`) and give two distinct reads. Same caller either way.
